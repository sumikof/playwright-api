# AI 支援開発 運用方針(playwright-api)

最終更新: 2026-07-26

> **FORK.md 分岐**: このファイルはテンプレートリポジトリ `playwright-api` の**テンプレート開発用**の
> 運用方針です。fork したリポジトリの直下に `FORK.md` が存在する場合、本ファイル(および
> `CLAUDE.md` / `AGENTS.md`)のテンプレート運用指示(Issue → Draft PR → Codex → … の一連の
> フロー)は適用せず、`FORK.md` の指示に従ってください。詳細は本文末尾の
> 「## fork の扱い」を参照してください。

本方針は、アップロード文書「AI支援開発プロジェクト運用方針書」(Issue → Draft PR → Codex
独立レビュー → 人間承認 → マージ の GitHub 中心フロー)と、本リポジトリで採用している
superpowers 流(spec → plan → 実装)を統合した折衷版として定義する。設計の背景・対象範囲・
確定した設計判断は
[`docs/superpowers/specs/2026-07-26-ai-workflow-policy-design.md`](../superpowers/specs/2026-07-26-ai-workflow-policy-design.md)
を参照。

## 役割

方針書の役割を、ソロ運用である本プロジェクトの担い手へ写像する。

| 方針書の役割 | このプロジェクトでの担い手 | 主な責任 |
|---|---|---|
| Issue作成者 / ユーザー / Maintainer | **ユーザー(sumikof)が兼務** | Issue 起票、設計承認、受け入れ確認、マージ |
| Claude Code | Claude Code | 調査・spec・plan・実装・テスト・PR 更新・指摘対応 |
| Codex | Codex(GitHub App) | 設計/最終の独立レビュー、Issue/spec/コード/テストの整合性確認 |
| CI | (当面なし) | ローカル `npm test` / `npx playwright test` を人間が確認 |

人間ゲートはユーザー1名が複数役割を兼務する。GitHub 上での「自分の PR を自分で Approve」は
できないため、**人間 Approve の必須化は行わず**、PR コメントによる設計承認・受け入れ確認を
人間ゲートとする。

## ドキュメント対応

方針書の用語を superpowers 資産へ写像し、二重管理を避ける。

| 方針書の用語 | このプロジェクトでの実体 |
|---|---|
| 設計書(`docs/design/issue-N-*.md`) | **spec** = `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md` |
| 実装計画 | **plan** = `docs/superpowers/plans/YYYY-MM-DD-<topic>.md` |
| ADR(`docs/decisions/ADR-*.md`) | 当面は spec 内「設計方針 / 未決事項」に集約。独立 ADR は必要時のみ |
| 共通基準(`docs/engineering-standards.md`) | **新規作成**。言語/ランタイム/固定バージョン方針/コード規約/検証コマンドを集約 |

- 方針書「設計書の標準項目」は spec テンプレートに取り込む。重い項目(トランザクション境界、
  移行・ロールバック等)は該当する変更のときのみ記載する。
- `CLAUDE.md` と `AGENTS.md` は共通基準を重複記載せず
  [`docs/engineering-standards.md`](../engineering-standards.md) を参照する。

## ワークフロー

方針書の 15 工程を superpowers に合わせて具体化する。

1. ユーザーが Issue 作成(`gh` 利用可)。背景・目的・対象/対象外・要件・受け入れ条件・制約を明記
2. Claude が作業ブランチを作成し、**bootstrap コミット(空コミット `git commit --allow-empty` 可)**を
   push してから **Draft PR** を作成(`Relates to #<N>`)。push は **HTTPS/gh 経由**。
   ※ base と差分ゼロのブランチでは PR を作成できないため、Draft PR 作成前に最低1コミットを置く
3. 設計 = `superpowers:brainstorming` → spec 作成・コミット・push → PR 本文へ反映
4. PR に `@codex review`(設計レビュー用テンプレ)を投稿
5. Claude が各指摘の妥当性を検証 → spec 修正。対応しない指摘は根拠を PR に記録
6. spec を修正したら最新コミットで `@codex review` を再実行する(レビュー対象を最新化)
7. ユーザーが PR で設計承認コメント(定型文)。**承認は「最後にレビューした内容」に対して行う**
   (レビュー後に spec を変更していれば手順6 で再レビューしてから承認)。承認前は実装しない
8. 承認後 = `superpowers:writing-plans` で plan 作成
9. **plan 整合性チェック(実装前ゲート、双方向)**:
   - (plan → spec)plan の各タスクが spec と受け入れ条件に対応すること
   - (spec → plan)spec の全要件・全受け入れ条件が、少なくとも一つの実装または検証タスクに
     対応していること(丸ごと欠落したタスクを検出する)
   不整合があれば原因で分岐する:
   - **plan 側の欠陥**(タスクの書き忘れ・余計なタスク等、承認済み spec 自体は妥当)
     → plan を修正し双方向チェックを再実行する(spec や承認は変更しない)
   - **新しい設計判断が必要 / spec 自体の変更が必要**(plan が spec に無い設計判断を追加、
     承認済み設計から逸脱、要件の過不足が spec 起因)
     → 実装に入らず spec を更新して §7 手順 4〜7(設計レビュー + 承認)へ戻す

   承認済み要件を削って plan に合わせる(整合性の帳尻合わせ)は禁止する。
10. `superpowers:executing-plans` または `superpowers:subagent-driven-development` で実装 + テスト
11. ブランチに base の最新を取り込む(`git fetch origin && git merge origin/<base>`、または
    `origin/<base>` へ rebase。引数なしの `git pull` は自ブランチの追跡先を取り込むだけで base は
    入らない点に注意)。そのうえでローカル検証(`npm test`, `npx playwright test` 等)を実行して
    結果を PR に記録し、Draft 解除する
12. `@codex review`(最終レビュー用テンプレ)を投稿する
13. **最終レビュー指摘の解消(受け入れの前提)**: 全指摘について Claude が妥当性を検証し、
    (a) 修正 → ローカル検証をやり直して再レビュー、または (b) 非対応の根拠を PR に記録して
    ユーザーが明示的に受け入れる、で決着させる。未決着の指摘が残る限り手順14へ進まない
14. ユーザー受け入れ確認(方針書のチェックリスト形式)
15. ユーザーがマージ(直前に `Closes #<N>` へ変更)。→ Issue close、残課題は別 Issue へ

### 設計レビューへ戻す条件(方針書 7.6 準拠)

公開 API/外部 IF 変更、データモデル変更、認証・認可方式変更、新規外部依存追加、
受け入れ条件変更、対象範囲拡大、性能・セキュリティ・運用への重大影響 —
これらが生じたら実装を止め、spec を更新して設計レビュー + ユーザー承認からやり直す。

## 整合の確認

自動ゲート(CI・ブランチ保護)が無い当面は、次の**原則を人間の目視チェックリスト**で担保する
(ソロ・単一 PR・低頻度運用では実務上これで十分)。

- **承認・受け入れ・マージは「最後にレビューした内容」に対して行う**。レビュー後に内容を変えたら
  やり直す — 設計フェーズは承認まで、実装フェーズは受け入れ・マージまでが対象。
  **受け入れ後に追跡対象ファイルを変えたら、再レビューだけでなく手順14のユーザー受け入れ確認も
  取り直す**(受け入れ後に別コミットを混ぜてマージし人間ゲートを迂回するのを防ぐ)
- **マージ前に base の最新を取り込む**(`git fetch origin && git merge origin/<base>`)。
  レビュー・検証は最新 base 込みの状態で行う
- 最終レビュー指摘は「修正して再レビュー」か「非対応根拠を記録+ユーザー受け入れ」で決着してから進む

> **厳密・原子的な保証**(承認/レビュー/マージ対象の SHA 完全一致、branch-up-to-date の強制、
> 人間確認〜マージ実行間の TOCTOU 排除)は、手動運用では原理的に完全化できない。これらは
> **CI の責務**とし、CI 導入時(必須ステータスチェック + branch-up-to-date 保護 +
> auto-merge / merge queue)に自動・原子的なゲートへ移管する(§8, §14)。当面はソロ運用の
> 低リスクを前提に残余を受容する。

## 自動ゲートと CI(次ステップ)

- CI・ブランチ保護は**当面導入しない**。当面のゲート = **ローカル検証コマンドの結果 +
  方針書チェックリスト + 人間の承認・受け入れ・マージ**(§7「整合の確認」の簡易・手動運用)。
- ただし **CI 導入は本方針の「推奨する次ステップ」**とする。手動での SHA/base 整合確認は
  厳密・原子的な保証を与えられず(§7・§14)、それを担うのは本来 CI だからである。
- **CI 導入時に移管する保証**(次ステップの具体像):
  - GitHub Actions で `npm test` / build(可能なら Playwright テスト)を必須ステータスチェック化
  - ブランチ保護: PR 経由必須 / CI グリーン必須 / **branch up-to-date 必須** / 未解決会話なし /
    force push 禁止 / main 直接 push 禁止
  - `auto-merge` / merge queue により **base/テスト整合を原子的に保証**する(最新 base を取り込んだ
    状態でテストが緑のものだけがマージされる)
- **CI で自動化できる範囲の限界**: 標準のブランチ保護(必須テスト + up-to-date)と merge queue が
  原子的に保証するのは **base 追随とテスト緑まで**。「Codex がレビュー済み」「ユーザーが受け入れ済み」を
  **その HEAD SHA に束縛**することは、これらだけでは担保されない(コメント形式のレビュー/受け入れは
  SHA に紐づかず、人間 Approve 必須化も見送るため)。これを自動化するなら、**受け入れ・レビュー対象
  SHA を検証する専用の必須 status check** を別途用意する必要がある。それを設けない当面は、
  「レビュー済み内容がそのままマージされる」ことは §7 の簡易・手動チェックリストで担保する。
- 人間 Approve の必須化はソロ運用では見送り(体制変化時に再検討)

## サブエージェント方針

- **同時 writer は主エージェントを含めて全体で1**とする(サブエージェントだけを数えるのではない)。
  ファイル・生成物・Git 状態を変更する作業は、主エージェント + サブエージェントを合わせて
  常に高々1つに限る(方針書 5.1 準拠)。
- **read-only の定義**: 作業ツリー・リポジトリ状態・Git 状態・生成物/キャッシュのいずれも
  変更しない操作(検索・読取・成果物を残さない解析等)。これらに限り複数を並列してよい。
- read-only 並列の上限はハーネスの既定同時実行数に従う。依存インストール、キャッシュ生成、
  `git` 状態の変更などを伴う調査コマンドは read-only とみなさず、直列の writer 枠で扱う。

## fork の扱い

方針ファイル(`CLAUDE.md` / `AGENTS.md` / `docs/engineering-standards.md` /
`docs/operations/ai-workflow-policy.md` / 将来の CI)は **upstream 所有**でありテンプレート開発用。

- fork は**これらを削除・編集しない**。削除・編集すると upstream merge 時に modify/delete または
  内容競合を招くため(既存の「demo-app は残す」方針と同じ理由)。
- **fork の opt-out は「fork 所有・upstream に存在しないマーカーファイル」で行う**:
  - fork はリポジトリ直下に `FORK.md`(upstream には存在しない、fork 所有)を作成し、
    自システムの運用を記述する。
  - upstream 所有の `CLAUDE.md` / `AGENTS.md` は**冒頭に次の分岐を明記**する:
    「**リポジトリ直下に `FORK.md` が存在する場合、本ファイルのテンプレート運用指示
    (Issue → Draft PR → Codex → …)は適用せず、`FORK.md` の指示に従う**」。
  - これにより、未変更の fork ではテンプレート運用が有効、opt-out したい fork は upstream 所有
    ファイルを一切触らず `FORK.md` を1つ追加するだけで切替できる(upstream が同ファイルを
    更新しても衝突しない)。
- README にもこの opt-out 手順(`FORK.md` を置く)を明記する。

> 補足: 冒頭に「参考扱い」と書くだけでは、未変更 fork でも AI ツールが root の
> `CLAUDE.md` / `AGENTS.md` を自動読込するため運用指示が実質有効になってしまう。マーカーファイルに
> よる明示的 opt-out はこの読込を分岐で無効化するための仕組みである。

## Codex レビュー依頼テンプレ

設計レビュー用・最終レビュー用の2種類の依頼文テンプレを用意する。いずれも本文冒頭を
`@codex review` から始め、PR コメントとして投稿する。プロジェクト固有の互換規則(固定バージョン
方針等)の具体的な内容は列挙せず、
[`docs/engineering-standards.md`](../engineering-standards.md) への適合確認を依頼する形にとどめる。

### 設計レビュー依頼テンプレ(§7 手順4・手順6)

```
@codex review

これは設計レビュー依頼です。以下の観点でレビューしてください。

- 対象: `docs/superpowers/specs/<YYYY-MM-DD-topic>-design.md`(Issue #<N> に対応)
- 確認してほしい点:
  - Issue に書かれた背景・目的・要件・受け入れ条件と spec の内容が整合しているか
  - 対象範囲・対象外の線引きが妥当か、対象外の理由が示されているか
  - 未決事項・リスクが網羅されているか、致命的な見落としがないか
  - `docs/engineering-standards.md` の固定バージョン方針・制約に適合しているか(適合確認のみ。
    具体的な規則の再掲は不要です)
- 指摘には重大度(must / should / nits)を付けてください
- 実装はまだ開始していません。設計段階の指摘のみで構いません
```

### 最終レビュー依頼テンプレ(§7 手順12)

```
@codex review

これは最終(実装)レビュー依頼です。以下の観点でレビューしてください。

- 対象: このPRの最新コミット(base ブランチ: `<base>`)
- 承認済み設計: `docs/superpowers/specs/<YYYY-MM-DD-topic>-design.md`
- 実装計画: `docs/superpowers/plans/<YYYY-MM-DD-topic>.md`
- 確認してほしい点:
  - 実装が承認済み spec・plan の内容から逸脱していないか
  - テストが受け入れ条件を実際に検証できているか(欠落がないか)
  - `docs/engineering-standards.md` の固定バージョン方針・検証コマンドに適合しているか
    (適合確認のみ。具体的な規則の再掲は不要です)
  - 重大なバグ・回帰・セキュリティ・パフォーマンス上の懸念
- ローカル検証結果(`npm test` / `npm run build` / `npx playwright test` 等)は PR 本文に
  記載済みです。あわせてご確認ください
- 指摘には重大度(must / should / nits)を付けてください。must 指摘は修正または非対応根拠の
  記録・ユーザー受け入れをもって決着させます
```
